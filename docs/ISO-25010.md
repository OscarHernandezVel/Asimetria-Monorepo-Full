# Aplicación de la norma ISO/IEC 25010 en Asimetría

Este documento registra **dónde** se aplicó cada característica de calidad del modelo de producto ISO/IEC 25010, **con qué objetivo**, **qué costo operativo** introduce y **qué evidencia** demuestra su cumplimiento. Parte de los RNF-01 a RNF-10 del documento *Sprint 2: Sistema de Inversión y Análisis Bursátil (Asimetría)* y cubre la pila completa: frontend (`apps/web`), API **Java 21 / Spring Boot** (`apps/api-java`; detalle en [BACKEND-JAVA.md](BACKEND-JAVA.md)), PostgreSQL + TimescaleDB, Redis y Nginx (`docker-compose.yml`), y la infraestructura de nube en AWS (`infra/aws`, [AWS.md](AWS.md)).

Las mediciones de carga (RNF-01, RNF-02, RNF-10) se tomaron sobre la pila real (`docker compose up -d`) en un portátil con Windows 11 y Docker Desktop (8 CPU y 6 GB asignados a la VM), con la **primera versión del backend (Python/FastAPI)**, que expone el mismo contrato REST y fue reemplazada por la API Java (queda en el historial de Git, commit inicial de `main`). Las pruebas automáticas (RNF-03, 04, 06, 09) ya corren contra la API Java. Repetir las mediciones de carga con la API Java queda pendiente (§5.8).

## 2. Defectos que encontraron las propias pruebas de calidad

Verificar los RNF contra la pila real, y no solo contra pruebas unitarias, destapó defectos que habrían llegado a producción. Se dejan registrados porque son la evidencia más concreta del valor del modelo ISO 25010 en este proyecto. Los defectos 1, 2, 5, 6, 8 y 9 se encontraron en la versión Python (v1); la columna «En la API Java» indica cómo se resolvió el mismo riesgo al reescribirla. Los defectos 10 a 14 aparecieron durante la reescritura en Java y la preparación para la nube.

| # | Detectado por | Defecto | Corrección | En la API Java |
|---|---|---|---|---|
| 1 | RNF-10 (arranque en limpio) | Con `uvicorn --workers N`, todos los procesos creaban el esquema y hacían la carga inicial a la vez: *deadlock* en PostgreSQL y un worker caído | `pg_advisory_lock` serializa el arranque | Flyway serializa las migraciones con su propio candado y `BloqueoDistribuido` hace que la carga inicial corra en una sola instancia |
| 2 | RNF-01 (100 usuarios) | Interbloqueo del pool de conexiones: con `get_db` síncrono, la liberación de la conexión necesita un hilo libre mientras todos los hilos esperan una conexión. Resultado: P95 de 15 s y 287 errores 504 | `get_db` asíncrono, pool dimensionado y `pool_timeout=5` → 503 inmediato | Hikari (`DB_POOL`, `connection-timeout` 5 s) + hilos virtuales; `ManejadorErrores` responde 503 con `Retry-After` |
| 3 | HU-10 CA-5 (API detenida) | La web se quedaba «Cargando…» 60 s (timeout por defecto de Nginx) | `proxy_connect_timeout 3s` en Nginx y `AbortSignal.timeout(10 s)` en el cliente | Igual (`apps/web/nginx.conf`, `ui.js`) |
| 4 | RNF-05 (reinicio con la API caída) | Nginx no arrancaba si `api` no resolvía por DNS: caía todo el sitio, incluso las páginas estáticas | Resolución en cada petición (`resolver 127.0.0.11` + variable) | Igual (`apps/web/nginx.conf`) |
| 5 | Seguridad (prueba de error 500) | Las respuestas 500 salían sin las cabeceras de seguridad (el handler corre fuera del middleware) | Las cabeceras se añaden también en los handlers de error | Spring Security las añade en el filtro, también en los errores (`rnf05HealthYCabecerasDeSeguridad`, `erroresConContratoDeLaApi`) |
| 6 | RNF-06 (Redis detenido) | Cada operación de caché esperaba su timeout: `/metrics/` tardaba 12 s y `/recommendations/` y `/cotizaciones` daban 504 | Timeouts de 0.5 s y *circuit breaker* de la caché (tras un fallo se omite Redis 10 s) | `AlmacenRedis` (misma pausa de 10 s, `siRedisFallaSeOmiteDiezSegundos…`) y `LoggingCacheErrorHandler` |
| 7 | Operación (equipo suspendido ~21 h) | La web servía las páginas desde un *bind mount* del disco `E:`. Al perderse el montaje en Docker Desktop, Nginx devolvía 500 «No such device» aunque la API seguía sana | Las páginas se copian dentro de una imagen propia (`apps/web/Dockerfile`), inmutable y portable, con *healthcheck* | Igual; en AWS la web se sirve desde S3 + CloudFront |
| 8 | Revisión de secretos (HU-01 CA-1) | `httpx` registraba en INFO la URL completa de cada petición; como Alpha Vantage exige la API key en la URL, la clave terminaba en los logs | Los loggers HTTP quedan en WARNING; una prueba verifica que `apikey=` nunca aparece en el log | `ProveedorAlphaVantage` enmascara la clave en errores y trazas (`alphaVantageLimitesErroresYClaveEnmascarada`) |
| 9 | Revisión de secretos (RNF-03) | Sin `JWT_SECRET`, cada uno de los 4 procesos generaba su propio secreto: los tokens fallaban al azar según el proceso que atendiera | La API se niega a arrancar sin `JWT_SECRET` | `PropiedadesAsimetria` exige ≥ 32 caracteres al arrancar; en AWS el secreto lo genera Terraform y es único para todas las tareas |
| 10 | Pruebas de integración (HU-07) | El login respondía 500: «cannot execute INSERT in a read-only transaction». La auditoría y el contador de intentos escriben dentro de un método marcado de solo lectura | Quitar `readOnly` del login | `AuthService.login`, `ca2LoginEntregaJwt…`, `bloqueoTrasCincoIntentos` |
| 11 | Revisión de código (HU-06) | Las alertas evaluadas desde el *listener* de cotizaciones no abrían transacción: la autollamada no pasa por el proxy de Spring y los cambios de estado de las reglas podían perderse | `@Transactional` en el propio *listener* | `EvaluadorAlertas.alActualizarCotizaciones` |
| 12 | Migración de la configuración (RNF-10) | `INTERVALO_COTIZACIONES=5` del `.env` existente (segundos en Python) se habría leído como **5 ms** en Spring: sincronizar 1.000 veces más seguido y agotar la cuota de Alpha Vantage | Unidad por defecto en segundos (`@DurationUnit`, `timeUnit = SECONDS`) | `PropiedadesAsimetria`, `TareasProgramadas`, `PropiedadesTest` |
| 13 | Revisión de seguridad para la nube (RNF-04) | La API confía en `CloudFront-Viewer-Address` para conocer la IP real. Detrás de Nginx, un cliente podía enviar esa cabecera y falsear su IP: evadir el límite por IP y la auditoría | Nginx la borra; en AWS solo CloudFront (que la fija) alcanza al ALB | `apps/web/nginx.conf`, `infra/aws/red.tf` |
| 14 | Revisión del despliegue (RNF-07) | `/docs` redirige a Swagger con una URL absoluta construida con el `Host` interno: detrás de CloudFront habría enviado al usuario al dominio privado del ALB (403) | Redirecciones relativas (`server.tomcat.use-relative-redirects`) | `application.yml` |

Además, la primera medición de RNF-01 con un generador de carga propio en Python daba P95 > 4 s incluso para un HTML estático servido por Nginx. El cuello de botella era el generador, no el sistema. Por eso la medición oficial se hace con **ApacheBench** (`ab`, imagen oficial `httpd`). Lección: hay que validar el instrumento de medición antes de interpretar la métrica.

## 3. Detalle por característica

### 3.1 Adecuación funcional (completitud · corrección · pertinencia)

**Dónde.**
- [`MotorCalculo`](../apps/api-java/src/main/java/co/edu/ucc/asimetria/dominio/calculo/MotorCalculo.java) contiene el motor de cálculo en Java puro: `betaAsimetrica` (HU-03), `retornoEsperadoCapm`, `volatilidad`, `maxDrawdown` y `perfilDesdeQuiz` (HU-07). La simulación (HU-05) está en `ResultadoSimulacion`, las recomendaciones (HU-04) en `MotorRecomendacion` + `PerfilRiesgo`, y las condiciones de alerta (HU-06) en `Condiciones`.
- La **beta** se calcula por regresión al origen sobre los días alcistas o bajistas del índice, Σ(rₐ·rₘ)/Σ(rₘ²). Con un solo dato equivale a rₐ/rₘ, que es el caso RiTech del documento (4/2 = **2.0**, 2.5/2 = **1.25**).
- El **retorno esperado** sale de CAPM: rf + β·(E[Rm] − rf), con E[Rm] histórico del índice. No es un número inventado.
- Las 36 operaciones REST cubren los 10 RF ([BACKEND-JAVA.md §2](BACKEND-JAVA.md#2-requerimientos-funcionales--código--prueba)). Las 9 vistas reproducen los 5 mockups y todos los apartados de la barra lateral.

**Objetivo.** Cumplir de forma exacta los criterios de aceptación, incluidos sus escenarios negativos.

**Costo operativo.** Las 85 pruebas deben mantenerse cuando cambia una regla de negocio. El cálculo vive en un único lugar (el servidor), así que no hay lógica duplicada en el cliente.

**Evidencia.** Ejecutar `mvn verify` en `apps/api-java`: cada prueba lleva el nombre de su HU y su CA (`hu03CasoRitechBetaAlcista2YBajista125`, `hu05Ca1Ca2Backtesting1040Y975`…). En la UI, el desglose de RiTech muestra +2 % → +4 % (2.00×) y −2 % → −2.5 % (1.25×), y el backtesting da **$1,040.00** y **$975.00**.

### 3.2 Eficiencia de desempeño

**Comportamiento temporal (RNF-01).**
- *Dónde:*
  - Caché Redis de métricas, análisis, recomendaciones y tarjeta destacada con TTL de 300 s (`@Cacheable` en [`MetricasService`](../apps/api-java/src/main/java/co/edu/ucc/asimetria/mercado/MetricasService.java), `AnalisisService` y `RecomendacionService`).
  - Invalidación al recalcular (`@CacheEvict` en `MetricasService.recalcular`).
  - Estructuras con la complejidad adecuada: `TopK` (O(n log k)), `Trie`, `SerieTemporal` (`TreeMap`); ver [BACKEND-JAVA.md §3](BACKEND-JAVA.md#3-estructuras-de-datos).
  - Gzip en Nginx y en la API; *debounce* de 250 ms en los filtros; las cotizaciones las calcula la tarea programada, no la petición.
- *Objetivo:* P95 ≤ 2 s con 100 usuarios.
- *Costo:* Redis (~4 MB de RAM en uso; límite configurado de 128 MB con LRU). Los datos pueden tener hasta 5 min de antigüedad hasta que se invalidan, cosa que ocurre siempre tras el recálculo diario.

**Utilización de recursos.**
- *Dónde:* una JVM por instancia con hilos virtuales y un pool Hikari de `DB_POOL` conexiones (20 en local, 10 por tarea en AWS). El frontend no usa librerías (gráficos SVG propios). El polling se pausa con la pestaña oculta y se reanuda al volver.
- *Costo:* con la v1 la pila consumía ~520 MB de RAM en reposo (api, worker y beat de Python ~400 MB). La API Java reemplaza esos tres procesos por uno (~300–400 MB estimados). El polling de 5 s genera 12 peticiones/min por usuario activo (1.200/min con 100 usuarios), todas servidas desde caché.

**Capacidad (RNF-02).**
- *Dónde:* en las migraciones de Flyway: [`V1__esquema_inicial.sql`](../apps/api-java/src/main/resources/db/migration/V1__esquema_inicial.sql) (PK `(time, empresa_id)` e índice B-Tree `(empresa_id, time DESC)`) y [`V2__SeriesTemporales`](../apps/api-java/src/main/java/db/migration/V2__SeriesTemporales.java) (hypertable con *chunks* de 30 días si hay TimescaleDB; índice BRIN en RDS). La prueba es [`benchmark_rnf02.sql`](../packages/db/benchmark_rnf02.sql).
- *Costo:* ~100–150 MB de disco por millón de filas.
- *Compresión:* `V2` activa la compresión nativa de TimescaleDB para *chunks* de más de 90 días (ahorra hasta 90 % de disco).

### 3.3 Compatibilidad (interoperabilidad · coexistencia)

**Dónde.**
- API REST JSON versionada (`/api/v1`, `snake_case`) con entradas validadas en [`Solicitudes`](../apps/api-java/src/main/java/co/edu/ucc/asimetria/web/Solicitudes.java) y publicadas automáticamente en OpenAPI por springdoc (`/openapi.json`, Swagger en `/docs`).
- El frontend solo conoce la API a través de [`market.js`](../apps/web/assets/js/market.js).
- El proveedor de datos es intercambiable (`PROVEEDOR=simulado|alphavantage`) detrás de la interfaz `ProveedorMercado` (`catalogo`, `historico`, `cotizaciones`, `dividendos`), ensamblada por `FabricaProveedores`.
- SendGrid se integra por HTTP.

**Objetivo.** Que clientes web, móviles o de terceros puedan integrarse con un contrato documentado.

**Costo.** Versionar la API cuando haya cambios incompatibles (`/api/v2`). El plan gratuito de Alpha Vantage limita a 5 peticiones/min, lo que obliga a subir `INTERVALO_COTIZACIONES`.

### 3.4 Usabilidad (operabilidad · accesibilidad · protección frente a errores)

**Dónde.**
- Tokens de color con contraste ≥ 4.5:1 ([`styles.css`](../apps/web/assets/css/styles.css)).
- Teclado: *skip link*, `:focus-visible`, pestañas con flechas y `<dialog>` nativo.
- Lectores de pantalla: ARIA (`aria-live`, `aria-sort`, `aria-current`, `role="alert"`).
- Diseño responsivo de 360 a 1920 px y respeto a `prefers-reduced-motion`.
- Mensajes de error del servidor en español y orientados a la acción («Este correo ya está en uso…», «El monto inicial debe ser mayor que 0»).
- Validación en dos capas: el cliente responde al instante y el servidor es la autoridad.

**Costo.** ~10 % más de marcado y una auditoría por vista nueva (~15 min).

### 3.5 Fiabilidad (madurez · disponibilidad · tolerancia a fallos · recuperabilidad)

**Dónde.**
- **Proveedor externo:** [`ProveedorResiliente`](../apps/api-java/src/main/java/co/edu/ucc/asimetria/mercado/proveedor/ProveedorResiliente.java) aplica 3 reintentos con *backoff* exponencial (150/300/600 ms). Tras 3 ciclos fallidos, [`CircuitBreaker`](../apps/api-java/src/main/java/co/edu/ucc/asimetria/mercado/proveedor/CircuitBreaker.java) se abre durante 30 s. Su estado se guarda en Redis y lo comparten todas las instancias.
- **Fallback:** se conserva el último precio en Redis o, si no hay, el último cierre de la base de datos (`CotizacionService.actuales`). La API nunca responde 500 por culpa del proveedor.
- **Alertas:** si falla el correo, la cadena `CanalCorreo → CanalEnApp` entrega en la app; si no hay eslabón que la entregue, la regla queda pendiente y `EvaluadorAlertas` la reintenta en la siguiente pasada (HU-06 CA-4).
- **Cierre diario:** `ON CONFLICT DO NOTHING` evita duplicados (HU-02 CA-3). Si el proveedor falla para un activo, se omite ese activo sin dañar lo guardado (CA-4).
- **Degradación controlada:**
  - BD saturada → 503 con `Retry-After` en 5 s.
  - API caída → Nginx sigue sirviendo la web y responde 502 en ~4 s; las vistas muestran el error y **Reintentar**.
  - Redis caído → *circuit breaker* de la caché: la API sirve desde la BD (200 en < 0.1 s) y el bloqueo de intentos de login queda desactivado mientras tanto (*fail-open*, para no impedir el acceso). Los precios en vivo se congelan en el último cierre.
- **Disponibilidad:** `/health` (BD + caché), *probes* de Actuator, *healthchecks* de Docker, `restart: unless-stopped`, apagado ordenado y tareas programadas bajo *advisory lock* (`BloqueoDistribuido`). En AWS: 2 zonas, autoescalado y rollback automático (§3.12).

**Objetivo.** 0 excepciones no controladas ante fallos externos; SLA del 99.5 %.

**Costo.** En el peor caso, un ciclo fallido tarda ~1 s antes de declarar los datos desactualizados, y con el circuito abierto los precios pueden tener hasta 30 s. El monitor externo cuesta entre US$0 y 10/mes (UptimeRobot) o ~2 USD/mes (health check de Route 53 en AWS).

**Inyección de fallos.** Configuración → *Inyección de fallos* (solo con `HERRAMIENTAS_PRUEBA=1`), o `docker compose stop api|redis`.

### 3.6 Seguridad (confidencialidad · integridad · no repudio · autenticidad · trazabilidad)

**Confidencialidad y autenticidad (RNF-03).**
- **Contraseñas:** se guardan con bcrypt de costo 12 (`BCryptPasswordEncoder` en [`SeguridadConfig`](../apps/api-java/src/main/java/co/edu/ucc/asimetria/config/SeguridadConfig.java), usado por `AuthService`). Se valida un máximo de 72 bytes, el límite de bcrypt.
- **Token:** JWT HS256 de 120 min firmado con `JWT_SECRET`, que viene del entorno y nunca del código.
- **Rutas protegidas:** todo `/api/**` exige JWT (Spring Security, *resource server*). Sin token o con un token caducado, alterado o de un usuario inexistente se responde 401 con `WWW-Authenticate: Bearer`.
- **Login:** mensaje genérico «Credenciales inválidas» y tiempo constante, porque se verifica contra un hash ficticio cuando el correo no existe y así no se pueden enumerar usuarios. Tras **5 intentos fallidos en 60 s** responde 429 (contador en Redis, compartido entre procesos).
- **Datos de cada usuario:** watchlist, alertas, simulaciones y auditoría se filtran por el usuario del token. Un recurso ajeno responde 404, no 403, para no revelar que existe.
- **Pago:** los datos de tarjeta **nunca llegan a la API**. El navegador solo envía el plan (`PUT /usuarios/me/plan`).
- *Costo:* ~250 ms de CPU por login o registro (bcrypt 12), es decir ~25 s de CPU para 100 logins simultáneos. Por eso las pruebas usan costo 4 (`BCRYPT_ROUNDS`).

**Integridad.**
- **Nginx** ([`apps/web/nginx.conf`](../apps/web/nginx.conf)) envía `Content-Security-Policy` estricta (`script-src 'self'`, sin scripts *inline*), `X-Frame-Options: DENY` y `frame-ancestors 'none'` (verificado: el navegador bloquea los iframes), `nosniff`, `Referrer-Policy` y `client_max_body_size 64k`.
- **Frontend:** todo texto dinámico pasa por `esc()` o `textContent`, y la redirección post-login solo acepta páginas locales.
- **API:** JPA y `JdbcTemplate` con parámetros (sin SQL concatenado). Bean Validation valida tipos, rangos y longitudes de cada `record` de entrada, y los CHECK y UNIQUE de PostgreSQL validan de nuevo. Los errores 500 no exponen detalles internos.
- **Contenedores:** la API corre como usuario sin privilegios (`uid 10001`). Solo Nginx publica un puerto, así que la API y la BD no son accesibles desde fuera.
- *Costo:* revisar la CSP cada vez que se añade un recurso externo. Swagger tiene su propia CSP relajada solo en `/docs`.

**Trazabilidad y no repudio (RNF-04).**
- [`AuditoriaService`](../apps/api-java/src/main/java/co/edu/ucc/asimetria/auditoria/AuditoriaService.java) escribe **a la vez** una línea JSON en stdout (CloudWatch Logs en AWS) y una fila en la tabla `auditoria`, en una transacción propia (`REQUIRES_NEW`) para que el evento quede aunque la operación falle.
- Campos: `ts` en UTC, `usuario_id`, `email`, `ip` (`IpCliente`: `CloudFront-Viewer-Address` en AWS o `X-Real-IP` de Nginx), `evento`, `estado` y `detalle`.
- Eventos auditados: REGISTRO, INICIO_SESION (éxito, error y bloqueo), CIERRE_SESION, CAMBIO_PERFIL_RIESGO, SUSCRIPCION, WATCHLIST_AGREGAR/ELIMINAR, PORTAFOLIO_ACTUALIZAR, SIMULACION, ALERTA_CREAR/ESTADO/ELIMINAR/DISPARADA y ALERTA_ENVIO.
- Retención: `TareasProgramadas.purgarAuditoria` borra a diario (03:00 UTC) los eventos con más de 90 días.
- *Costo:* ~250 B por evento, unos 110 MB por trimestre con 100 usuarios activos, más el almacenamiento del centralizador (US$0–25/mes).

### 3.7 Mantenibilidad (modularidad · reusabilidad · analizabilidad · modificabilidad · capacidad de prueba)

**Dónde.**
- Capas separadas ([BACKEND-JAVA.md §1](BACKEND-JAVA.md#1-arquitectura-por-capas)):
  - `dominio`: Java puro, sin E/S ni Spring.
  - `usuario`, `mercado`, `alerta`: casos de uso.
  - `web`: HTTP.
  - `mercado.proveedor`: integración externa intercambiable (Factory + Adapter + Decorator).
  - `auditoria`, `comun.almacen`, `tareas`: transversales.
- El frontend accede a la API solo desde `market.js` y `ui.js`.
- El esquema lo versiona Flyway y Hibernate verifica al arrancar que las entidades coincidan (`ddl-auto: validate`); las pruebas de integración lo comprueban contra PostgreSQL real.
- Configuración 12-factor (`.env`, [`.env.example`](../.env.example)).
- Datos simulados **deterministas** (semilla fija) para que las pruebas sean reproducibles.
- [CI](../.github/workflows/ci.yml): `mvn verify` (JaCoCo ≥ 80 %), `terraform validate` y el build de las imágenes. **85 pruebas, 95 % de cobertura de líneas.**

**Costo.** Unos minutos de CI por *push* (capa gratuita; las pruebas de integración levantan PostgreSQL). Cada cambio de esquema exige una migración nueva y ajustar la entidad. Se aceptó ese costo porque evita una divergencia silenciosa entre el esquema de producción y el código.

### 3.8 Portabilidad (adaptabilidad · instalabilidad · reemplazabilidad)

**Dónde.**
- [`docker-compose.yml`](../docker-compose.yml) levanta 4 servicios con imágenes fijadas por versión: `timescale/timescaledb:2.17.2-pg16`, `redis:7.4-alpine`, `nginx:1.27-alpine` y `eclipse-temurin:21-jre`. La API y la web se construyen como imágenes inmutables, sin depender de archivos del host en tiempo de ejecución.
- *Healthchecks* y `depends_on: service_healthy` garantizan el orden de arranque, y la carga inicial es idempotente.
- Una sola imagen de API: las tareas programadas corren dentro de ella (sin worker ni beat).
- La misma imagen corre en Compose y en ECS Fargate; solo cambian las variables de entorno. La migración `V2` se adapta a TimescaleDB o a RDS.

**Objetivo.** Despliegue homogéneo en desarrollo, pruebas y producción con un solo comando y en menos de 5 min.

**Costo.** ~1 GB de imágenes la primera vez y ~1 h/mes para actualizar las imágenes base.

### 3.9 Trazabilidad de los datos e integraciones externas (Seguridad → trazabilidad, Fiabilidad)

- **Llamadas externas:** cada petición a Alpha Vantage y a SendGrid queda en la tabla `llamadas_externas` (proveedor, operación, éxito, HTTP, latencia) y en el log JSON. La API key nunca se guarda: los errores se enmascaran con `***` ([`ProveedorTrazado`](../apps/api-java/src/main/java/co/edu/ucc/asimetria/mercado/proveedor/ProveedorTrazado.java), [`ProveedorAlphaVantage`](../apps/api-java/src/main/java/co/edu/ucc/asimetria/mercado/proveedor/ProveedorAlphaVantage.java), `AuditoriaService.registrarLlamada`). Retención de 90 días.
- **Procedencia de cada precio:** cada fila de `precios_historicos` guarda `fuente` (SIMULADO, ALPHAVANTAGE o COTIZACION_VIVO) y `fecha_ingesta`, es decir, de dónde vino y cuándo se almacenó.
- **Entrega de correos:** cada notificación guarda `estado_envio` y el `X-Message-Id` de SendGrid, con el que se rastrea la entrega en el panel de SendGrid.
- **Cuota de Alpha Vantage:** un contador diario en Redis (`AV_LIMITE_DIARIO`) deja de llamar antes de agotar el plan. Los datos almacenados siguen sirviéndose.
- **Almacenamiento:** compresión columnar de TimescaleDB para *chunks* de más de 90 días. Las migraciones de Flyway quedan registradas en `flyway_schema_history` (qué versión, cuándo y con qué *checksum*); una base creada por la v1 se adopta como versión 2 sin perder datos.
- **Visibilidad:** `GET /api/v1/integraciones` muestra el estado, la cuota usada, el P95 de latencia, las llamadas recientes y el origen de los precios. `POST /integraciones/probar` verifica las claves; SendGrid se prueba en *sandbox mode*, sin enviar correos.
- *Costo:* ~150 B por llamada externa; una consulta de cuota a Alpha Vantage por cada prueba manual.

### 3.10 Borde de producción (Seguridad, Eficiencia, Portabilidad)

- **Caddy** ([`deploy/Caddyfile`](../deploy/Caddyfile)): certificados automáticos, **solo TLS 1.3** (cierra el pendiente de RNF-03), HTTP/3, HSTS y compresión zstd/gzip.
- **Nginx:** IP real del cliente detrás del proxy y límites por IP (15 req/s en la API, 10 req/min en `/auth`), además de las cabeceras de seguridad.
- **Banderas separadas:** `MODO_DEMO` (cuenta demo) y `HERRAMIENTAS_PRUEBA` (inyección de fallos). En público se puede ofrecer la demo sin que nadie apague los servicios para todos.
- **`docker-compose.prod.yml`:** usa imágenes inmutables de GHCR, publica solo los puertos 80/443, hace un backup diario con `pg_dump` (7 días de retención) y rota los logs.
- **[`deploy.yml`](../.github/workflows/deploy.yml):** construye las imágenes y despliega por SSH solo si CI pasó; luego verifica `/health`. El *rollback* se hace con `TAG=<sha> ./deploy/desplegar.sh`.
- La guía completa está en [`DESPLIEGUE.md`](DESPLIEGUE.md). *Costo:* dominio US$10–15 al año y VPS de 2 vCPU/4 GB por ~US$5–12 al mes.

### 3.11 Backend Java: estructuras de datos y patrones (Mantenibilidad, Fiabilidad, Eficiencia)

- **Dónde:** `apps/api-java`. La tabla completa RF → clases → pruebas y los diagramas de llamadas entre archivos están en [BACKEND-JAVA.md](BACKEND-JAVA.md).
- **Modularidad y reusabilidad:** capas `web → servicios → dominio`. El dominio (β, CAPM, perfiles, condiciones de alerta, simulación) es Java puro, sin Spring, y se prueba sin contexto.
- **Modificabilidad:** patrones Strategy (perfiles, condiciones, almacén), Factory (proveedor según `PROVEEDOR`), Adapter (Alpha Vantage), Decorator (trazado + resiliencia), Chain of Responsibility (correo → en app), Observer (eventos de cotizaciones y catálogo) y Builder (simulación). Agregar un perfil, una condición o un canal es **una clase nueva**, sin tocar las existentes.
- **Comportamiento temporal y utilización de recursos:**
  - `TopK` con montículo: O(n log k) en vez de ordenar todo.
  - `Trie`: autocompletar en O(L + r).
  - `SerieTemporal` sobre `TreeMap`: rango O(log n + r) y alineación por fecha O(n + m).
  - `BufferCircular`: *ticks* con memoria acotada.
  - `CacheLRU` + `TokenBucket`: límite de tasa O(1) con memoria acotada ante IP variadas.
  - Hilos virtuales de Java 21.
- **Tolerancia a fallos en varias instancias:** el circuit breaker, la cuota de Alpha Vantage y el bloqueo de login viven en Redis, compartidos. `pg_try_advisory_lock` garantiza que cada tarea programada corra una vez por ciclo aunque haya N tareas ECS. Esto reemplaza a Celery worker + beat.
- **Corrección:** `PropiedadesAsimetria` valida la configuración al arrancar (`JWT_SECRET` ≥ 32 caracteres). Flyway versiona el esquema y Hibernate lo valida (`ddl-auto: validate`).
- *Costo (estimado, sin medir en AWS):* imagen de ~330 MB (JRE 21 + dependencias) y ~300–400 MB de RAM por instancia en reposo (JVM). El arranque con Flyway y la carga inicial queda cubierto por el `start-period` de 90 s del healthcheck y la gracia de 120 s del ALB. Las pruebas de integración son más lentas que las unitarias porque levantan PostgreSQL real.

### 3.12 Nube AWS (Fiabilidad, Seguridad, Eficiencia, Portabilidad)

- **Dónde:** `infra/aws` (Terraform) y `.github/workflows/deploy-aws.yml`. La tabla de cada recurso con su característica, objetivo y costo está en [AWS.md §2](AWS.md#2-recursos--isoiec-25010).
- **Disponibilidad (RNF-05):**
  - 2 tareas Fargate en 2 zonas detrás de un ALB con health check de *readiness*.
  - Autoescalado 2 → 6 tareas.
  - *Circuit breaker* de despliegue con rollback automático.
  - Health check externo de Route 53 cada 30 s, con alarma por correo.
- **Recuperabilidad:** RDS con restauración a un punto en el tiempo (7 días), *snapshot* final y protección contra borrado. Versionado de la web en S3 e imágenes inmutables en ECR.
- **Confidencialidad e integridad (RNF-03):**
  - Solo CloudFront es público. El ALB acepta únicamente las IP de CloudFront con una cabecera secreta.
  - API, BD y caché están en subredes privadas.
  - TLS de extremo a extremo (`sslmode=verify-full` hacia RDS, TLS en Valkey).
  - Cifrado en reposo.
  - Secretos en Secrets Manager.
  - WAF con reglas OWASP gestionadas y límites por IP.
  - Despliegue por OIDC, sin claves de larga duración.
- **Trazabilidad (RNF-04):** la IP real llega a la auditoría por `CloudFront-Viewer-Address`. Hay logs JSON en CloudWatch (30 días) y cada acción de despliegue queda en CloudTrail.
- **Instalabilidad (RNF-10):** `terraform apply` crea ~90 recursos. CI valida `fmt` y `validate` en cada *push*.
- *Costo:* **~150 USD/mes** por defecto y ~210 USD/mes con alta disponibilidad completa (desglose en AWS.md). Lo más caro son las tareas Fargate, el NAT y el ALB.

## 5. Limitaciones y trabajo pendiente

1. **Proveedor real.** `ProveedorAlphaVantage` está implementado y probado con respuestas simuladas (`MockRestServiceServer`), pero no se probó con una API key real. Su plan gratuito no cubre el índice ^NDX, así que se usa el ETF QQQ como aproximación.
2. **RNF-02, peor caso.** La agregación sobre el millón completo se mantuvo < 500 ms en 3 de 4 corridas (mediana 437 ms, máximo 513 ms en un portátil con Docker Desktop). Para garantizarla con margen se recomienda un *continuous aggregate* de TimescaleDB (resumen mensual precalculado), que reduce esa consulta a milisegundos.
3. **WebSocket.** El documento propone WebSocket para tiempo real. Se implementó *polling* cada 5 s, más simple y suficiente para 100 usuarios (P95 < 0.7 s). WebSocket queda como mejora si crece el número de usuarios.
4. **OAuth2 (Google/Apple)** y los pagos por **transferencia/PayPal** son solo de interfaz. El cobro real requiere una pasarela que tokenice la tarjeta (PCI DSS).
5. **Lighthouse.** Falta registrar la puntuación oficial de accesibilidad (≥ 90). Ya se verificaron etiquetas, nombres accesibles, contraste y ausencia de desbordamiento a 360 px.
6. **TLS 1.3.** En el servidor único, Caddy acepta solo TLS 1.3 (`deploy/Caddyfile`). En AWS, CloudFront negocia TLS 1.3 con los navegadores actuales y exige como mínimo TLS 1.2 (`TLSv1.2_2021`) por compatibilidad. Falta desplegar con un dominio real y verificarlo en SSL Labs. En local la pila se sirve por HTTP.
7. **Revocación de JWT.** El token no tiene estado: cerrar sesión lo descarta en el navegador y queda auditado, pero el token sigue siendo válido hasta que expira (máximo 120 min). Si se necesita revocación inmediata, se puede añadir una lista negra en Redis.
8. **Mediciones de carga con la API Java.** RNF-01 y RNF-10 se midieron con la v1 (Python). Hay que repetir `ab -n 2000 -c 100` contra la API Java (local y en AWS) y actualizar la tabla del §1.
